# AGENTS.md — Context for AI Agents Working on This Repo

This file is context for future agent sessions (Cursor, or otherwise) working on this
repository. Read it before making changes. It explains what this project is, where
content actually lives, and the workflow conventions established so far.

## What this repo is

This repo (`github.com/shassen/resume`) is the source for **Shawn Hassen's interactive
resume website** — a dark, motion-forward, single-page site built with static
HTML/CSS/vanilla JS (no framework, no build step). It's deployed via **GitHub Pages**
at **https://shassen.github.io/resume/**.

It is explicitly *not* a styled clone of a print resume. The design brief was: "portfolio
meets resume" — dark/edgy aesthetic, scroll-reveal animations, an interactive experience
timeline, skill chips, and a featured project treated as a hero card. See
[index.html](index.html) for the full content structure (hero, about, experience,
skills, featured project, education, contact).

## Two-file content model — read this before editing content

There are **two separate documents that must be kept in sync manually**, because they
serve different purposes and live in different places:

1. **This site** — [index.html](index.html), [styles.css](styles.css),
   [main.js](main.js) — the interactive webpage, tracked in this repo.
2. **The print resume** — a separate, plain, print-oriented one/two-page HTML resume
   used to generate the downloadable PDF. It intentionally looks nothing like the
   website (Helvetica, black-on-white, no CSS animations) — it's meant to look like a
   normal resume when printed or opened in a PDF viewer.
   - **Master file location (outside this repo):**
     `/Users/shawn/Documents/shawn-hassen-resume/resume.html`
   - This file is the **source of truth for resume content and wording**. When
     resume-affecting content changes (job bullets, skills, education, dates,
     locations), it should be edited there first (or in lockstep with `index.html`).
   - After editing it, the PDF must be **regenerated** (see below) and the regenerated
     PDF copied into this repo, because the site's "Download PDF" button and the nav's
     "Résumé ↓" link both point at the dated PDF (e.g. `shawn-hassen-resume-august-2026.pdf`)
     that lives in this repo, not the Documents folder.

**Practical implication:** almost any content change (a new job bullet, a skill
addition, a location change, wording tweaks) needs to be applied in *three* places to
stay consistent:

- [index.html](index.html) — the relevant section on the website
- `/Users/shawn/Documents/shawn-hassen-resume/resume.html` — the print resume master
- The dated resume PDF in this repo — regenerated from the master (see command below)

Pure styling/interaction/layout changes to the website (animations, timeline visuals,
colors, spacing) only touch this repo and do **not** need to be mirrored to the print
resume — the print resume has its own much simpler CSS and is not meant to visually
match the site.

### Regenerating the PDF

The PDF is generated by headlessly printing `resume.html` to PDF (matching its own
`@page` rules: Letter size, 0.5in margins), then copied into this repo. This is
persisted as a script — run it from the repo root whenever `resume.html` changes:

```bash
./scripts/regenerate-resume-pdf.sh
```

It uses Playwright's CLI (`npx playwright pdf`) rather than a repo dependency, so
nothing is added to this static site's shipped code; Chromium is downloaded to npx's
cache on first run if not already present. The output filename is dated with the
current month and year (e.g. running it in October 2026 produces
`shawn-hassen-resume-october-2026.pdf`) — the script deletes the previous dated PDF
(in both the master Documents folder and this repo) and rewrites every
`shawn-hassen-resume-<month>-<year>.pdf` reference in `index.html` to match, so there's
always exactly one correctly named/linked PDF. It also prints a page-count sanity
check.

Sanity-check page count after any content addition — the print resume should stay at
**2 pages** (it was already 2 pages before most edits in this project's history; that's
been treated as acceptable given the amount of real content, but avoid pushing it to 3).

## Content accuracy rules

- **Never invent accomplishments.** Several roles (originally Zoom and Solvvy) started
  as `[TODO]` placeholders on the print resume because the user hadn't supplied real
  bullets yet. Wait for the user to provide real detail (they've supplied it via
  markdown summaries, verbal descriptions, etc.) rather than fabricating specifics.
- Zoom bullets in particular went through several rounds of revision based on direct
  feedback:
  - Started concrete/feature-heavy, then reframed around role requirements and
    transferable skills (ownership, security/compliance, SDLC rigor) rather than just
    "features shipped."
  - Domain-specific jargon (e.g. "RBAC", "scheduling-group access control", literal
    persona names like "agents/supervisors/admins") was deliberately generalized to
    broader, role-agnostic language so the resume reads well outside the WFM domain.
  - Career-milestone details (original engineering-team member pre-GA, $1M+ MRR, ZP2→ZP3 promotion) are
    real facts supplied by the user — treat these as accurate and preserve them; don't
    soften or drop the specific numbers.
- When a role has a notable one-line status (e.g. "Acquired by Zoom" for Solvvy,
  "Promoted from ZP2 to ZP3" for Zoom), it's rendered as a small italic accent-colored
  note directly under the role title/dates — not as a bullet. This is
  `.entry-note` in the print resume and `.timeline-note` on the site. Follow this
  pattern for similar one-line status callouts in the future rather than adding a bullet
  for it.

- **Print resume** (`resume.html`): Employment → Skills → Education → Projects (header

## Design system (website only)

- **Palette:** near-black (`#0b0b0d`) background, off-white text, acid-lime accent
  (`--accent`, `#d4ff3f`) for CTAs/highlights/glow, violet (`--accent-2`, `#7c5cff`) as a
  secondary gradient color. Defined as CSS variables at the top of
  [styles.css](styles.css).
- **Type:** Space Grotesk (display/headings), Inter (body), JetBrains Mono (labels,
  dates, `// comment`-style eyebrows) — loaded from Google Fonts in `index.html`.
- **Motion:** IntersectionObserver-based scroll-reveal (`.reveal` / `.in-view`), active-
  nav-link tracking, magnetic CTA buttons, a mouse-reactive hero glow, and the
  experience timeline described below. Everything is gated behind
  `prefers-reduced-motion` and `(pointer: fine)` checks in [main.js](main.js) — preserve
  this when adding new interactions.

### Experience timeline (the trickiest part of this codebase)

The timeline (`.timeline` in `index.html`, styled in `styles.css`, driven by
`main.js`) intentionally has **no numbered markers** — each role is a hollow dot that
fills solid (with a gentle pulse animation) once scroll progress reaches it, and the
connecting line is drawn incrementally as segments *between* dots rather than as one
continuous line, specifically so the line never visually passes through a dot.

If you touch this again, know the coordinate math is fiddly:

- `.timeline-dot` sits at `left: -40px` relative to its `.timeline-item` (`<li>`), 16px
  wide → its center is at `-32px` relative to the `<li>`.
- The connecting line segments are `::before` (static track) / `::after` (animated
  fill) pseudo-elements on each `.timeline-item` (not on the parent `<ul>` — that was
  tried and caused the line to run through the dots because of stacking order). They
  must be positioned at `left: -33px` (2px wide, so center is also `-32px`) to align
  with the dot exactly. If you change the dot's size/position, recompute this.
- `main.js` computes scroll progress and, for each item, decides whether it's `reached`
  (dot fills) and which one is `current` (slightly scaled up), then sets a per-segment
  `--segment-fill` custom property so each inter-dot line segment fills independently
  rather than one global bar.
- Dots use `z-index: 1`, line segments use `z-index: 0`, so dots always render on top.

## Git workflow conventions established in this project

- The user works on **short-lived feature branches** per change (e.g.
  `dev-update-resume-with-zoom-content`, `dev-add-solvvy-details`,
  `dev-fix-resume-format`, `dev-fix-employment-bullets`,
  `dev-fix-zoom-work-location`), then opens a PR into `main` and merges via GitHub
  (`gh pr list` shows PRs #1–#5, all merged as of this writing).
- **Agents should not commit or push without being explicitly asked.** The established
  pattern in this project: make the file edits, regenerate/sync the PDF if resume
  content changed, run a quick local visual QA pass (see below), and leave changes as
  uncommitted working-tree modifications for the user to review with `git diff` /
  `git status` before they commit and push themselves. Only commit/push when the user's
  message clearly asks for it.
- The user sometimes pre-creates the feature branch themselves before asking for
  changes — check `git branch --show-current` and `git status` at the start of a task
  rather than assuming you're on `main`.

## Local QA workflow

There's no test suite (it's a static site). The established QA pattern for visual
changes:

1. Serve the repo root locally, e.g. `python3 -m http.server 8123` (background it —
   don't block on it).
2. Use Playwright (headless Chromium) from `/tmp` (it's not a repo dependency, so
   `npm install playwright` in a scratch dir like `/tmp` if not already present) to
   navigate, scroll to the relevant section, and screenshot it for visual review.
3. Watch for `prefers-reduced-motion` correctness — verify content is immediately
   visible (no reliance on scroll-triggered reveal) when that media feature is set.
4. Check both desktop (~1280–1440px) and mobile (~390px) viewports for layout changes.
5. Clean up scratch scripts/screenshots and kill the background server when done.

Don't add Playwright or its browsers as a repo dependency — it's only ever been used
as an ad hoc local QA tool, not part of the shipped site.

## Deployment

GitHub Pages is enabled on this repo (`Settings → Pages`, source: `main` branch,
`/ (root)`), publishing automatically on every push to `main`. The `.nojekyll` file at
the repo root tells Pages to skip Jekyll processing and serve the static files as-is —
keep it. All asset paths in `index.html`/`styles.css` are relative, which is required
since the site is served from a subpath (`/resume/`), not a domain root.
